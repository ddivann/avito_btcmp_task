# План решения задачи по классификации ботов

Основание: [условие](task0.txt), [стартовый ноутбук](bot_detection_challenge/quickstart.ipynb), [официальная метрика](bot_detection_challenge/metric.py). Рабочая папка с данными — `bot_detection_challenge/`.

## Цель и условия

Для каждой `cookie_id` из `data/test.csv` получить `score` от 0 до 1: чем выше оценка, тем вероятнее трафик известного сервиса автоматизированного сбора данных. Признаки рассчитываются по событиям **только внутри суточного окна** куки: `window_start_ts <= event_ts < window_end_ts`.

Главная метрика — **максимальный Precision среди порогов с Recall ≥ 0,70**. Считать её функцией `precision_at_recall` из `metric.py`: равные оценки обрабатываются одной группой. Порог в ответе не нужен.

Ограничения: нельзя использовать внешние API, модели крупнее 1 млрд параметров, ручную разметку теста, ответы по конкретным ID и чужие решения. Все используемые open-source библиотеки и подходы нужно назвать в описании. Итог должен воспроизводиться с фиксированным `random_state`, зафиксированными зависимостями и указанной версией Python. На отправку — максимум **7 попыток**.

## Этап 3. Построить надёжную таблицу признаков

1. Загрузить метаданные train/test и события с корректными типами дат и чисел. Сохранить исходный порядок тестовых строк для ответа.
2. Соединить события с границами окна по `cookie_id`. Оставить только события с `window_start_ts <= event_ts < window_end_ts`; события за концом окна не должны участвовать ни в одном признаке.
3. Привести варианты регистра `platform` к общему виду. Для категориальных полей явно обозначить отсутствие значения. Числовые `search_page`, `pointer_x`, `pointer_y` преобразовать с обработкой некорректных строк.
4. Сортировать события по времени внутри куки перед вычислением пауз и порядка действий. При одинаковых `event_ts` не приписывать событиям выдуманный достоверный порядок.
5. Рассчитать одинаковым кодом признаки для train и test. Соединять агрегаты с полным списком кук через `left join`, чтобы ни одна кука не исчезла.
6. Заполнить признаки для кук без применимых событий осмысленно: счётчики — нулями, отсутствие условного измерения — отдельным индикатором или специальным значением.
7. Отдельно проверить два варианта обработки полных дубликатов: с сохранением и с удалением. Сравнить результат на временной валидации; не считать дубликаты автоматически ошибкой логирования.

**Защита от утечки:** не использовать `target`, сам `cookie_id`, события после окончания окна, статистику будущих меток и кодирование категорий, обученное на валидационных метках. Возраст куки рассчитывать относительно момента окна, а не относительно сегодняшней даты.

## Этап 4. Настроить валидацию до подбора сложной модели

Тест расположен позже обучения. Поэтому случайное перемешивание кук даст менее честную оценку переноса на будущие дни.

| Срез | Обучающие окна | Проверочные окна | Для чего |
| --- | --- | --- | --- |
| Ранний | 6–13 апреля | 14–16 апреля | Разработка признаков и первичный отбор идей |
| Основной | 6–16 апреля | 17–19 апреля | Итоговое локальное сравнение решений; 1 951 кука, 160 ботов |

- [ ] Для каждой проверки обучать модель только на более ранних датах.
- [ ] Считать основную метрику через `precision_at_recall` из `metric.py` на уровне кук. Отдельно записывать число найденных ботов и отмеченных кук при лучшем допустимом пороге для понимания результата.
- [ ] Для диагностики считать PR-AUC и ROC-AUC, но выбирать итоговый вариант по основной метрике и устойчивости на двух срезах.
- [ ] Зафиксировать метрику baseline до добавления новых признаков. Константная оценка на основном срезе соответствует доле ботов около 8,2%; это ориентир, а не целевой результат.
- [ ] Не подбирать решение многократно только под основной срез: это приведёт к переобучению на локальную проверку.

**Результат этапа:** любой новый набор признаков можно сравнить с baseline одинаковым способом. На отправку пока не тратятся попытки.

## Этап 5. Создавать признаки по приоритету

Добавлять группы последовательно, сохраняя результат до и после каждой группы. Полезны счётчики, доли от числа релевантных событий и индикаторы отсутствия данных. Для отношений предусмотреть деление на ноль.

### 5.1. Базовая активность

- Общее число событий, счётчики каждого `event_name`, число активных часов.
- Число событий в час максимальной активности; число активных минут.
- Возраст куки к началу окна (`window_start_ts - cookie_created_at`).
- Доли типов событий: просмотры объявлений, выдачи, контакты, избранное, капча и т. д.

### 5.2. Временной ритм

- Минимум, медиана, квантили и разброс интервалов между последовательными событиями.
- Доля интервалов 0–1, 1–5 и 5–30 секунд; доля одинаковых временных меток.
- Максимум событий за минуту и за короткий промежуток; длительность активности от первого до последнего события.
- Доля активности по часам суток и ночью; число условных сессий, разделённых, например, паузой более 30 минут.
- Для признаков времени сравнить абсолютные значения с нормировкой на общее число событий: высокая активность сама по себе может быть недостаточным объяснением.

### 5.3. Разнообразие и повторяемость

- Число уникальных `item_id`, категорий, локаций, типов продавцов и поисковых запросов.
- Отношение уникальных объявлений к числу просмотров; доля повторных просмотров; максимум просмотров одного объявления.
- Доли наиболее частых категорий и локаций; мера концентрации интересов, если она улучшает проверочную метрику.
- Глубина `search_page`, число уникальных страниц и доля просмотров глубоких страниц выдачи.

### 5.4. Последовательность действий

- Частота переходов между типами событий: «выдача → объявление», «объявление → контакт», повторные просмотры.
- Доля объявлений, после которых было контактное действие, если связь событий можно определить без неоднозначности.
- Соотношения «просмотры / контакты», «поиски / просмотры», «избранное / просмотры».
- Последовательности при совпадающих секундах трактовать осторожно: порядок таких событий может быть неизвестен.

### 5.5. Платформа, User-Agent и курсор

- Нормализованная платформа, число платформ и смен платформы в течение окна.
- Из `user_agent` извлечь широкие категории браузера, ОС и устройства; число разных User-Agent за окно. Сырые строки высокой размерности сначала не использовать.
- Для `pointer_x`/`pointer_y`: доля заполненных координат среди применимых событий, число уникальных точек, повторяемость координат. Проверить связь пропусков с платформой.
- Отдельно проверить влияние `captcha_shown` и `login`: эти события доступны внутри окна, но модель может чрезмерно зависеть от одной технической особенности.

**Порядок работ при ограниченном времени:** сначала активность и ритм, затем разнообразие и сценарии, затем более сложные признаки User-Agent и курсора.
